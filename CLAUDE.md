# Obsidian Vault Performance - навигация по проекту

Этот документ - карта проекта. Читай его в начале каждой сессии,
чтобы понимать, где что лежит и как с этим работать.

## Что это за проект

**Obsidian Vault Performance** - набор инструментов для семантического анализа
хранилища знаний (Obsidian vault).
Строит таксономию доменов на основе содержимого файлов и выводит результат
в веб-дашборд (`dashboard.html`).

## Порядок чтения в начале любой сессии

1. `CLAUDE.md` (этот файл) - правила репо, инструменты, навигация
2. `.claude/plans/` - технические планы, если задача уже начата
3. `.claude/retrospectives/` - память проекта. файлы с резюме прошлых доработок
4. `.claude/skills/*/SKILL.md` - логика конкретного навыка перед его вызовом

## Структура репозитория

obdidian_vault_performance/

## Инструменты

Python (python-dotenv, pyyaml), локальный HTTP-сервер (`python -m http.server`)
для раздачи `dashboard.html`, Claude Code agents/skills для анализа vault.

## Правила репо

1. Анализ доменов vault - только через Agent tool (`vault-domain-analyzer`,
   `vault-topic-classifier`) либо через суб-агента `llm` по схеме из правила 8,
   никогда не читать/писать файлы домена вручную (Read/Write в основном
   потоке). См. `feedback_agent_delegation` в памяти.
2. Не публиковать без явной команды от меня.
3. `git add` поимённо. Никогда `git add .` или `git add -A`.
4. `.env` не читать целиком. Для проверки переменной - `grep "^VAR=" .env`.
5. Не выводить сырой JSON анализа в чат - только обработанное summary.
6. Временные файлы анализа живут в `.claude/temp_files/`, чистятся `cleanup.py`.
7. Мусорные файлы (шаблоны, вложения, пустые заметки) отсеиваются до Фазы 2
   двумя ступенями (эвристика без LLM + сигнал `vault-topic-classifier`) и
   никогда не анализируются доменами. Список отсеянного - в секции
   `filtered_out` итогового `taxonomy.json`, проверять её при подозрении,
   что фильтр отсёк что-то ценное.
8. Делегирование тяжёлых фаз суб-агенту `llm` (см. `~/.llm/orchestrator.md`):
   перед тяжёлым шагом любого skill (генерация/рефакторинг кода >100 строк,
   многошаговая разработка, анализ логов, а также Фазы 0.2 и 2
   `semantic-taxonomy` - самые тяжёлые части проекта) один раз за сессию
   проверь доступность через `llm-ssh test`. Если связь есть - отправляй
   такой шаг через `llm`/`llm --fresh` по схеме из
   `.claude/skills/semantic-taxonomy/SKILL.md` (разделы Фаза 0.2 и Фаза 2),
   результат интегрируй и проверяй локально. Если связи нет или команда
   `llm` отсутствует - работай как раньше: через Agent tool
   (`vault-topic-classifier` / `vault-domain-analyzer`) для этих двух фаз.
   Vault принадлежит пользователю, а песочница `llm` - его же подписка,
   поэтому отправка содержимого туда разрешена; правило 1 (анализ доменов
   только через Agent tool ИЛИ через `llm` по этой схеме, никогда вручную
   Read/Write в основном потоке) остаётся в силе.
9. Спека (speckit-* скиллы, `.specify/`, `specs/`) - никогда не коммитить
   и не добавлять в гит. Спека это инструменты и арифакты для планирования,
   не часть релиза основного функционала. Работай со спекой локально,
   в отдельных сессиях, не смешивай с основным кодом.

## Большая фича = план в `.claude/plans/`

Любая задача дольше часа оформляется планом в папке `.claude/plans/`:
1. Имя файла: `YYYY-MM-DD-название-функции.md`.
2. План делится на фазы. У каждой фазы статус `[ ]` или `[x]`.
3. В конце плана - итог: реализован целиком или нет, что осталось.

## Цикл в конце каждой фичи

После завершения каждой фичи прогони 5 ходов:
1. Найди ошибки → докажи примером → исправь.
2. Что упустили (граничные случаи, проверка входных данных, обработка ошибок).
3. Это реальная проблема нашего проекта? Сверь с `.claude/plans/`.
4. Свежий взгляд - перечитай diff, как будто видишь впервые.
5. Security review. Особенно: персональные данные + материалы третьих лиц
   (содержимое чужого vault).

## Рефлексия в конце сессии

В `.claude/retrospectives/YYYY-MM-DD_краткое-название.md` запиши:
1. Какая задача была.
2. Как решали.
3. Решили - да / нет / частично.
4. Что можно было лучше.
5. Что узнал нового о пользователе или проекте.
