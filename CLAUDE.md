# Obsidian Vault Performance - навигация по проекту

## Что это за проект

**Obsidian Vault Performance** - инструменты семантического анализа
хранилища знаний (Obsidian vault): таксономия доменов по содержимому файлов,
результат в веб-дашборд (`dashboard.html`).

В начале сессии прочитай `.claude/plans/` (планы задачи),
`.claude/retrospectives/` (память проекта), `.claude/skills/*/SKILL.md`.

## Правила репо

1. Анализ доменов vault - только через Agent tool (`vault-domain-architect`,
   `vault-domain-analyzer`) либо через суб-агента `llm` по правилу 8, никогда не
   читать и не писать файлы домена вручную (Read/Write в основном потоке).
2. Не публиковать без явной команды от меня.
3. `git add` поимённо. Никогда `git add .` или `git add -A`. Ветки - правило 12.
4. `.env` не читать целиком. Для проверки переменной - `grep "^VAR=" .env`.
5. Не выводить сырой JSON анализа в чат - только обработанное summary.
6. Временные файлы анализа живут в `.claude/temp_files/`, чистятся `cleanup.py`.
7. Каждый `.md` файл vault обязан быть учтён ровно один раз. При подозрении на
   потери проверяй арифметикой: `metadata.total_files` + `projects.count` +
   `unclassified.count` + `filtered_out.count` = `metadata.all_files_count`.
   Ту же сумму проверяет `candidates_accounted` (`--verify`) и шапка дашборда.
   Второй уровень - `files_exist`: путь должен существовать в vault, иначе верный
   счёт скрывает опечатку. Секции: `projects` - практика проектов,
   `unclassified` - домен не назначен (`reason` и `suggestion`), `filtered_out` -
   отсеянный шум (проверяй, если фильтр мог отсечь ценное). Навигационные хабы
   (файлы из одних ссылок) мусором НЕ считаются - идут в `unclassified`.
   Мусор фильтрует `--scan` (Фаза 1.1) ДО агента: служебные папки, пустые
   заметки, `embed_only`. Агенту список приходит очищенным.
8. Тяжёлые шаги (генерация/рефторинг кода >100 строк, многошаговая разработка,
   анализ логов, классификация Фазы 1 и Фазы 2 `semantic-taxonomy` - самые
   тяжёлые части проекта) делегируй суб-агенту `llm`: один раз за сессию
   проверь `llm-ssh test`, при успехе отправляй по схеме из
   `.claude/skills/semantic-taxonomy/SKILL.md` (см. `~/.llm/orchestrator.md`),
   результат интегрируй и проверяй локально. Нет связи или нет команды `llm` -
   работай через Agent tool. Vault принадлежит пользователю, песочница `llm` -
   его же подписка, поэтому отправка содержимого туда разрешена.
   Модель передаётся явно: каждый вызов `llm` идёт с префиксом
   `LLM_MODEL=<алиас модели оркестратора>` (алиасы и детали - в разделе про
   модель песочницы в `SKILL.md`). Не полагайся на дефолт песочницы и
   `~/.llm/config`: без префикса песочница может работать на другой модели.
   Исключение - `llm clean` и `llm-ssh test`, им модель не нужна.
9. Спека (speckit-* скиллы, `.specify/`, `specs/`) - никогда не коммитить и не
   добавлять в гит: инструменты планирования, не часть релиза. Работай с ней
   локально, в отдельных сессиях.
10. Инкрементальное обновление (`synthesize_taxonomy.py --merge`) работает от
    дельты. Dirty = новые и изменённые файлы: `status` `new | changed` в
    `vault-scan.json` (`--scan --new-only` сверяет хеш файла с `content_hash` узла
    `topic-graph.json`, для записей `projects`/`unclassified` - с `content_hash` из
    `taxonomy.json`) - единственный источник «что нового». Без графа прогон
    полный. Источник состояния - `taxonomy.json`, `domain-map.json`, граф.
    - Структура пересматривается дёшево, по накопленным данным, без чтения
      старых текстов: `build_domain_cards.py` (`domain-cards.json`) ->
      `vault-domain-architect` в режиме инкремента -> `patch.json` ->
      `apply_domain_patch.py`. Тексты читаются только у дельты и записей
      `unclassified`/`projects`.
    - Глубокий анализ (`vault-domain-analyzer`, режим «добавление») - только
      дельта. Старые записи файлов берутся из `taxonomy.json`.
    - Фаза 3б: переоценка тем затронутых доменов (`vault-topic-reassessor`),
      ответ проверяет `validate_reassessed_topics.py`. Незатронутые домены
      сохраняют темы как есть.
    - Граф `build_topic_graph.py` строго после Фаз 2, 3 и 3б. Без свежих
      `{domain_id}-analysis.json` и `{domain_id}-topics.validated.json` он не
      запускается, `--merge` не запускается без графа новее `vault-scan.json`
      и `domain-map.json`.
    - `--merge` - без LLM: домены собираются из актуальной раскладки, парадигмы,
      `global_facets`, статистика и learning paths пересчитываются кодом.
      `taxonomy.json` пишется только при выполненных инвариантах, кеш - после него.
    - `relevance_required` из `graph-dirty-domains.json` - новые файлы без свежего
      анализа домена; для них вызывается `vault-relevance-finder`, ответы
      применяются через `--apply-relevance`, он `graph-dirty-domains.json` не
      меняет. Связи `dependency` из анализа и `related`/`dependency` от
      субагента `dirty_domains` не задают.
    - `--merge --full` пересчитывает прогресс всех доменов без dirty-фильтра, но
      по-прежнему мёржит. `build_topic_graph.py --full` стирает связи, полученные
      от субагента.
    Порядок и защиты - в `.claude/skills/semantic-taxonomy/SKILL.md`.
11. Агенты работают без ограничения времени, ждать можно сколько угодно.
    - `tools.subagent({run_in_background: true})` - по умолчанию и только так.
      Блокирующий `false` уносит агента вместе с собой по лимиту времени.
    - Не держи агента внутри той же программы, где он запущен: прерывание
      программы останавливает и его (`was stopped before it finished`).
      Запустил - программа вышла - собирай отдельным вызовом.
    - Признак готовности - файл на диске, а не текст ответа: `domain-map.json`,
      `{domain_id}-analysis.json`. Дублируй через `list_agents`.
    - Пока агент работает, длинных вызовов инструментов не делай.
    - Агент молча остановился - не начинай заново: `send_message` вернёт его
      в контекст, он продолжит с уже собранным материалом.
12. Любое изменение файлов проекта - только в feature-ветке. Мастер-ветка здесь -
    `main` (`origin/main`). Никогда не редактируй файлы проекта, находясь на
    `main`, даже для "мелкой правки".
    - Перед первым изменением проверь `git branch`: нет feature-ветки - создай
      `git switch -c feature/<описание-задачи>`, есть подходящая - переключись на
      неё. Вторую ветку на ту же задачу не создавай.
    - Коммит, пуш и вливание в мастер - только по моей явной команде. Никогда не
      мёржь и не удаляй ветку самостоятельно.
    - По команде на пуш: `git add` поимённо (правило 3), коммит в ветке, затем
      `git switch main` → `git merge --no-ff feature/<имя>` (без pull-request) →
      `git push origin main`.
    - После пуша и релиза ветка удаляется: `git branch -d feature/<имя>` и
      `git push origin --delete feature/<имя>`.
13. Новая фича - в отдельной feature-ветке. Перед первой правкой под новую фичу:
    - если есть любая ветка, отличная от `main` - новую не создавай, работай
      в существующей (`git switch feature/<имя>`), даже если её название
      относится к другой задаче;
    - если веток, отличных от `main`, нет - создай от `main`:
      `git switch -c feature/<описание-фичи> main`.
    Незакоммиченные изменения чужой задачи в новую ветку не переноси без команды.

## Архитектура

Скрипты ведут оркестрацию, LLM-агенты - только экспертный анализ контента.
Скрипты не вызывают модель, агенты не пишут код. Speckit (`.specify/`,
`specs/`) - подсистема управления фичами, в релиз не входит (правило 9).

## Большая фича = план в `.claude/plans/`

Любая задача дольше часа оформляется планом: имя файла `YYYY-MM-DD-название-функции.md`,
фазы со статусом `[ ]` или `[x]`, в конце - итог: реализовано целиком или что осталось.

## Цикл в конце каждой фичи

1. Найди ошибки → докажи примером → исправь.
2. Что упустили: граничные случаи, входные данные, обработка ошибок.
3. Это реальная проблема проекта? Сверь с `.claude/plans/`.
4. Свежий взгляд - перечитай diff, как будто видишь впервые.
5. Security review: персональные данные и материалы третьих лиц.

## Рефлексия в конце сессии

В `.claude/retrospectives/YYYY-MM-DD_краткое-название.md` запиши: какая была задача, как решали,
решили - да / нет / частично, что можно было лучше, что нового узнал о проекте.
