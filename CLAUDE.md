# Obsidian Vault Performance - навигация по проекту

Этот документ - карта проекта. Читай его в начале каждой сессии,
чтобы понимать, где что лежит и как с этим работать.

## Что это за проект

**Obsidian Vault Performance** - набор инструментов для семантического анализа
хранилища знаний (Obsidian vault).
Строит таксономию доменов на основе содержимого файлов и выводит результат
в веб-дашборд (`dashboard.html`).

## Порядок чтения в начале любой сессии

1. `CLAUDE.md` (этот файл) - правила репо, инструменты, навигация
2. `.claude/plans/` - технические планы, если задача уже начата
3. `.claude/retrospectives/` - память проекта. файлы с резюме прошлых доработок
4. `.claude/skills/*/SKILL.md` - логика конкретного навыка перед его вызовом

## Инструменты

Python (python-dotenv, pyyaml), локальный HTTP-сервер (`python -m http.server`)
для раздачи `dashboard.html`, Claude Code agents/skills для анализа vault.

## Правила репо

1. Анализ доменов vault - только через Agent tool (`vault-domain-analyzer`,
   `vault-topic-classifier`) либо через суб-агента `llm` по схеме из правила 8,
   никогда не читать/писать файлы домена вручную (Read/Write в основном
   потоке). См. `feedback_agent_delegation` в памяти.
2. Не публиковать без явной команды от меня.
3. `git add` поимённо. Никогда `git add .` или `git add -A`.
4. `.env` не читать целиком. Для проверки переменной - `grep "^VAR=" .env`.
5. Не выводить сырой JSON анализа в чат - только обработанное summary.
6. Временные файлы анализа живут в `.claude/temp_files/`, чистятся `cleanup.py`.
7. Мусорные файлы (шаблоны, вложения, пустые заметки) отсеиваются внутри
   Фазы 1, до Фазы 2, двумя ступенями (эвристика без LLM в
   `collect_vault_structure.py --prepare-batches` + сигнал
   `vault-topic-classifier` на шаге классификации) и никогда не
   анализируются доменами. Список отсеянного - в секции `filtered_out`
   итогового `taxonomy.json`, проверять её при подозрении, что фильтр отсёк
   что-то ценное.
8. Делегирование тяжёлых фаз суб-агенту `llm` (см. `~/.llm/orchestrator.md`):
   перед тяжёлым шагом любого skill (генерация/рефакторинг кода >100 строк,
   многошаговая разработка, анализ логов, а также шаг классификации внутри
   Фазы 1 и Фаза 2 `semantic-taxonomy` - самые тяжёлые части проекта) один
   раз за сессию проверь доступность через `llm-ssh test`. Если связь есть -
   отправляй такой шаг через `llm`/`llm --fresh` по схеме из
   `.claude/skills/semantic-taxonomy/SKILL.md` (разделы Фаза 1 и Фаза 2),
   результат интегрируй и проверяй локально. Если связи нет или команда
   `llm` отсутствует - работай как раньше: через Agent tool
   (`vault-topic-classifier` / `vault-domain-analyzer`) для этих двух шагов.
   Vault принадлежит пользователю, а песочница `llm` - его же подписка,
   поэтому отправка содержимого туда разрешена; правило 1 (анализ доменов
   только через Agent tool ИЛИ через `llm` по этой схеме, никогда вручную
   Read/Write в основном потоке) остаётся в силе.
9. Спека (speckit-* скиллы, `.specify/`, `specs/`) - никогда не коммитить
   и не добавлять в гит. Спека это инструменты и арифакты для планирования,
   не часть релиза основного функционала. Работай со спекой локально,
   в отдельных сессиях, не смешивай с основным кодом.
10. При инкрементальном обновлении (`synthesize_taxonomy.py --merge`)
    переанализируются только dirty-домены из `graph-dirty-domains.json`
    (Фаза 1.4). Topics не-dirty доменов остаются как есть, topics
    переанализированных доменов полностью пересчитываются (новый анализ
    заменяет старый). Пустой `dirty_domains` - Фаза 2 и мёрж пропускаются
    целиком, `taxonomy.json` не меняется.

## Архитектура слоёв: Python + LLM агенты

Проект использует гибридную архитектуру: **детерминированные Python-скрипты** для
оркестрации + **LLM-агенты** для анализа контента.

### Слой 1: Оркестрация (Python скрипты, детерминированная логика)

Это НЕ аналитические скрипты, а утилиты для подготовки данных и работы с графами:

- `collect_vault_structure.py` — сканирование vault, фильтр мусора (шаблоны,
  пустые заметки), группировка в батчи. Нужны системные операции + кеширование
  по content-hash, LLM не требуется.

- `build_topic_graph.py` — построение графа тем/доменов, определение dirty-доменов
  для инкрементального режима. Чистая логика графов (diff), LLM не требуется.

- `synthesize_taxonomy.py` — финализация (фазы 3-6): объединение анализов доменов,
  выявление глобальных иерархий, построение learning paths, валидация целостности JSON.

### Слой 2: LLM-анализ (Claude Code агенты)

Это экспертный анализ контента — только здесь нужен LLM:

- `vault-topic-classifier` (агент) — классификация файлов батча по доменам (Фаза 1).
  Проверяет фрагментацию на лету (семантическую близость доменов, анализ папок
  с файлами из разных доменов) до создания нового домена — без отдельного
  постфактум-скрипта.

- `vault-domain-analyzer` (агент) — полный анализ файлов одного домена (Фаза 2).
  Заполняет 12+ полей (essence, role, type, dependencies, learning_paths и т.д.).

- `vault-relevance-finder` (агент) — поиск related/dependencies для новой заметки.

### Слой 3: Speckit (управление фичами, НЕ входит в основной функционал)

Отдельная подсистема для разработки фич: скрипты, навыки, шаблоны. Работать
локально, не коммитить (см. правило 9).

### Почему разделение на слои

1. **Детерминизм** — оркестрационные скрипты дают одинаковый результат каждый раз.
   LLM-агенты могут немного варьироваться, но скрипты обеспечивают структуру.

2. **Оптимизация** — скрипты вычисляют dirty-домены, агенты анализируют только их.
   Без этого каждый incremental запуск переанализировал бы всё.

3. **Отладка** — ошибку в классификации легче найти, если она в агенте, а не спрятана
   в цепочке скриптов.

## Большая фича = план в `.claude/plans/`

Любая задача дольше часа оформляется планом в папке `.claude/plans/`:
1. Имя файла: `YYYY-MM-DD-название-функции.md`.
2. План делится на фазы. У каждой фазы статус `[ ]` или `[x]`.
3. В конце плана - итог: реализован целиком или нет, что осталось.

## Цикл в конце каждой фичи

После завершения каждой фичи прогони 5 ходов:
1. Найди ошибки → докажи примером → исправь.
2. Что упустили (граничные случаи, проверка входных данных, обработка ошибок).
3. Это реальная проблема нашего проекта? Сверь с `.claude/plans/`.
4. Свежий взгляд - перечитай diff, как будто видишь впервые.
5. Security review. Особенно: персональные данные + материалы третьих лиц
   (содержимое чужого vault).

## Рефлексия в конце сессии

В `.claude/retrospectives/YYYY-MM-DD_краткое-название.md` запиши:
1. Какая задача была.
2. Как решали.
3. Решили - да / нет / частично.
4. Что можно было лучше.
5. Что узнал нового о пользователе или проекте.
