# Классификация и кластеризация батча файлов (Фаза 1: Ingest + Classify)

Тебе передан `batch_id` и список файлов одного батча (относительные пути от
корня vault + имена + content_hash). Батчи
обрабатываются оркестратором строго последовательно — к моменту твоего
вызова все предыдущие батчи уже дописали свои домены в
`domain-vocabulary.json`. Ты уже находишься в изолированном субагенте —
оркестратор не увидит ничего из твоего процесса, только финальный ответ.

Это объединённый шаг: раньше классификация тем и кластеризация по доменам
были разделены (отдельный скрипт группировал файлы по теме уже после всех
батчей). Теперь сквозная кластеризация по доменам — твоя работа: ты сразу
решаешь, к какому домену относится каждый файл, сверяясь со словарём
доменов, накопленным предыдущими батчами.

## Шаг 0: Проектирование архитектурной карты доменов (только если словарь пуст)

Если `domain-vocabulary.json` пуст (ты первый батч) — прежде чем читать файлы
по одному, сделай один проход по всем файлам батча: заголовки + первый
абзац каждого. Цель — спроектировать 5-10 доменов **дисциплинарного уровня**,
а не завести домен от первого попавшегося файла.

**Правило "техника vs дисциплина"**: домен называется по инженерной задаче,
которую решает содержимое, а не по конкретному методу/структуре/алгоритму,
которым эта задача решается в одном файле. Если тянет назвать домен по
технике — поднимись на уровень выше и спроси "а что это за техника решает".

Примеры (для калибровки, не ограничивающий список):
- star schema, snowflake schema, dimensional modeling → домен **DWH-моделирование**
  (не "типы схем")
- nested loop join, hash join, merge join, индексы, план запроса → домен
  **Оптимизация запросов** (не "методы соединения", не "индексирование")
- партиционирование, шардирование, репликация → домен **Хранение и масштабирование**
  (не "партиционирование")
- ETL, ELT, dbt, Airflow → домен **Инженерия данных / пайплайны**
  (не "инструменты ETL")

Если содержимое батча не похоже ни на один из этих примеров — спроектируй
домены по той же логике: функция/дисциплина, а не техника и не глава учебника.
Эта карта — твоя рабочая гипотеза, не финал: следующие батчи могут её
расширить (новый домен) или ты сам можешь скорректировать её по ходу этого
же батча, если видишь, что ошибся. Пользователя ни о чём не спрашивай —
решение принимаешь сам, по контексту содержимого.

## Шаг 1: Определение пути к vault

Прочитай `.env` в корне проекта, возьми значение `VAULT_PATH` (без кавычек) и
подставляй его перед каждым относительным путём файла батча — итоговый путь
должен быть абсолютным.

## Шаг 2: Чтение текущего словаря доменов

Прочитай `.claude/temp_files/domain-vocabulary.json`. Формат:

```json
{
  "domains": [
    {
      "domain_id": "dwh-basics",
      "domain_name": "Основы DWH",
      "description": "Концепции хранилищ данных: факты, измерения, ETL."
    }
  ]
}
```

Если файла нет или он пустой — значит ты первый батч, словарь пуст,
начинаешь его с нуля.

## Шаг 3: Чтение и классификация каждого файла батча

Для каждого файла прочитай содержимое через Read tool. Если файл длинный
(несколько тысяч строк), можно ограничиться заголовками, первыми ~200
строками и первым абзацем каждого раздела — для определения домена файла
полное чтение обычно не требуется. Не выводи содержимое файлов в ответ.
Анализируй содержимое как оно есть, не по названию папки или файла.

Для каждого файла выполни это **ЭКСПЕРТНЫЙ** анализ классификации:

1. **ОБЯЗАТЕЛЬНО сначала сверь файл против ВСЕХ существующих доменов словаря**
   — прочитай `domain_name` и `description` каждого и реши, подходит ли по
   смыслу содержимое файла хотя бы одному из них. Заводить новый домен, не
   проверив существующие, **категорически запрещено**.

2. **КРИТИЧЕСКИ: Анализ на фрагментацию (прежде чем создавать новый домен)**
   
   Если файл НЕ подходит существующим доменам, ПЕРЕД созданием нового домена:
   
   а) **Анализ семантической близости**: есть ли в словаре домены, которые
      семантически ПОХОЖИ, но имеют немного разные описания? (Пример: 
      "dimensional-modeling" vs "medallion-architecture" оба про архитектуру DWH)
      Если да — выбери ОДИН из них, даже если файл подходит не идеально. 
      Объединение лучше, чем фрагментация.
   
   б) **Анализ папки**: проверь, в какой папке находится файл. Если файлы
      этой же папки уже распределены по РАЗНЫМ доменам, это красный флаг
      фрагментации. В этом случае файл должен пойти в домен, где уже есть
      другие файлы из этой папки (даже если подходит слабее).
   
   в) **Таблица решений**: 
      - Файл подходит под несколько существующих доменов? → выбери САМЫЙ ПОДХОДЯЩИЙ
      - Файл создаёт NEW область (явно не подходит ни под один)? → создай новый домен
      - Файл слабо подходит под один домен, но папка указывает другой? → следуй папке

3. Если существующий домен подходит (или выбран по логике выше) — используй
   его `domain_id` без изменений (не меняй его название/описание ради одного файла).

4. Если ни один не подходит (после анти-фрагментационных проверок выше) —
   заведи новый домен: `domain_id` (slug из 2-4 английских слов через дефис,
   устойчивый, не привязанный к имени файла), `domain_name` (короткое
   название, на языке содержимого), `description` (1 предложение, что входит
   в домен). Это правило одинаково для Full и Incremental режимов — как при
   добавлении книги на полку: сначала ищем подходящую существующую, и только
   если не нашли — заводим новую.

   **Перед тем как зафиксировать новый домен**, проверь его название по
   правилу "техника vs дисциплина" из Шага 0: это дисциплина/функция или
   конкретный метод/структура/алгоритм? Если второе — поднимись на уровень
   выше и назови домен по задаче, которую техника решает (см. примеры
   в Шаге 0). Эта проверка обязательна для каждого нового домена, не только
   в первом батче.
   **ДОБАВЬ ПРИМЕЧАНИЕ**: "Создан из батча {batch_id}, файл {filename}. 
   Проверить на объединение с похожими доменами на Фазе 1.4."
   Добавь домен в свою рабочую копию словаря.

5. Если уверенность в домене низкая (файл слишком короткий, смешанный по
   темам, неоднозначный) — файл тоже уходит в `unclassified` с причиной
   `low_confidence`, а не в случайный домен.

Дополнительно для каждого успешно классифицированного файла определи:

- `essence` — одно предложение, о чём файл (на языке содержимого).
- `key_concepts` — список ключевых понятий файла (2-5 элементов).
- `folder_path` — папка, в которой находится файл (для анализа фрагментации)

## Шаг 4: Обработка ошибок чтения

Если файл повреждён, пуст или не читается — не включай его в `assignments`
итогового JSON, а отметь в `skipped` с полем `reason` (`"read_error"` или
`"empty_or_too_short"`). Это не `unclassified` — настоящий мусор, который
никогда не получит домен.

## Шаг 5: Запись результата на диск

Критически важно: используй Write tool для обоих файлов.

Сначала `.claude/temp_files/batch-{batch_id}-assignments.json`:

```json
{
  "batch_id": "{batch_id}",
  "assignments": [
    {
      "path": "относительный/путь/файла.md",
      "folder": "папка",
      "domain_id": "dwh-basics",
      "essence": "...",
      "key_concepts": ["...", "..."],
      "fragmentation_notes": "опционально: если выбор домена был обоснован логикой избежания фрагментации, отметить здесь"
    }
  ],
  "unclassified": [
    {"path": "относительный/путь.md", "reason": "low_confidence", "folder": "папка"}
  ],
  "skipped": [
    {"path": "относительный/путь.md", "reason": "read_error", "folder": "папка"}
  ],
  "new_domains": ["dwh-basics"],
  "fragmentation_analysis": {
    "folders_with_multiple_domains": [
      {"folder": "DWH", "domains_found": ["dimensional-modeling", "medallion-architecture"], "recommendation": "объединить в dwh-architecture"}
    ]
  }
}
```

`new_domains` — список `domain_id`, которые ты завёл в этом батче.
`fragmentation_analysis` — опциональное поле, если агент обнаружил потенциальную фрагментацию (файлы одной папки в разных доменах).

Затем перезапиши `.claude/temp_files/domain-vocabulary.json` целиком —
старые домены без изменений + твои новые добавленные в конец. Не удаляй и не
переименовывай домены, заведённые предыдущими батчами.

Не выводи полный JSON ни одного из файлов в ответ — это перегрузит контекст
оркестратора.

## Шаг 6: Возврат краткой сводки

⚠️ Критически важно — формат ответа.

Запрещено выводить в ответ: полный JSON, таблицы по файлам, списки всех
файлов батча, блоки кода с JSON.

Должно быть в ответе — ровно 3 строки, ничего больше:
- Строка 1: `Батч: {batch_id}`
- Строка 2: `Файлы: [N] классифицировано, [U] unclassified, [K] пропущено`
- Строка 3: `Домены: [список domain_id использованных в батче через запятую] (новых: [M])`
