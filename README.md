# Obsidian Vault Performance

Инструмент для семантического анализа хранилища знаний Obsidian (vault).
На основе содержимого файлов строит таксономию доменов, типов контента,
learning paths и фасетной навигации, а результат показывает в веб-дашборде.

**[🔗 Живое демо дашборда](https://a95d.github.io/obdidian_vault_performance/demo/dashboard.demo.html)**
на фейковых данных — показывает, как выглядит результат анализа.

## Зачем это нужно

Со временем хранилище заметок разрастается: конспекты, статьи, проекты, идеи. Поиск находит заметку, если вы помните нужное слово. Но он не покажет, какие темы у вас вообще есть, где знания тонкие и что стоит изучить дальше.

Проект читает содержимое заметок (не только названия и папки) и отвечает на такие вопросы:

- **Какие темы у меня есть?** Заметки группируются в домены, например «Базы данных» или «Продуктивность».
- **Насколько я проработал каждую тему?** Для тем видно глубину проработки и пробелы.
- **Что потерялось?** Заметки, которым не нашлось места, попадают в отдельные списки, и их видно.
- **В каком порядке учить?** Строятся маршруты обучения: что идёт раньше, а что опирается на предыдущий материал.
- **Что связано?** Заметки получают связи друг с другом.

Результат открывается в дашборде `dashboard.html`: это карта ваших знаний, где можно фильтровать заметки по темам и типам и смотреть маршруты обучения.

Пример: в хранилище 75 заметок. Инструмент может сказать, что 54 из них разложены по 9 темам, 13 относятся к практике проектов, 4 не легли ни в одну тему (с подсказкой, какую тему завести), а 4 отсеяны как пустые или служебные. Сверка чисел нужна, чтобы ни одна заметка не пропала молча.

Полезно, если заметок много и хочется навести порядок или понять, чего не хватает. Если заметок мало, проще просмотреть их вручную.

## Что делает

1. Сканирует ваш Obsidian vault по указанному пути.
2. Отсеивает файлы, не относящиеся к реальным знаниям — служебные папки,
   пустые заметки, файлы-заготовки и заметки, состоящие только из вставок
   изображений. Отсев детерминированный, без обращения к LLM.
3. Проектирует карту доменов по всему материалу за один проход: агент
   `vault-domain-architect` собирает словари заметок, определяет границы
   доменов и раскладывает файлы по темам.
4. Глубоко анализирует каждый домен — агент `vault-domain-analyzer` заполняет
   12+ полей на заметку и строит темы с оценкой проработки и пробелами.
5. Строит `taxonomy.json` — домены, типы, зависимости, маршруты обучения.
   Файлы, которым не назначен домен, не теряются: практика проектов попадает в
   секцию `projects`, неназначенное — в `unclassified`, отсеянный шум — в
   `filtered_out`. Проверка `candidates_accounted` следит, чтобы каждый
   `.md` файл vault был учтён ровно один раз.
6. Показывает результат в `dashboard.html` — интерактивной карте вашего vault.

## Требования

- Python 3.12+
- Claude Code (для запуска анализа через агента `vault-domain-analyzer`)
- Установленный Obsidian vault с `.md` файлами

## Установка

1. Склонируйте репозиторий и перейдите в папку проекта.
2. Установите python-зависимости:

   ```bash
   pip install -r requirements.txt
   ```

3. Скопируйте `.env.example` в `.env` и укажите путь к вашему vault:

   ```env
   VAULT_PATH=C:\path\to\Obsidian Vault
   ```

## Первый запуск

Анализ запускается через Claude Code, а не напрямую скриптами:

1. Откройте проект в Claude Code.
2. Попросите: **"построй таксономию"** (или похожую фразу — см. триггеры
   в `.claude/skills/semantic-taxonomy/SKILL.md`).
3. Навык `semantic-taxonomy` спросит режим анализа:
   - **Full** — полная пересборка (первый запуск, смена `VAULT_PATH`).
   - **Incremental** — добавление только новых файлов.
4. Дождитесь завершения всех фаз анализа. Результат — `.claude/temp_files/taxonomy.json`.

Анализ выполняют два агента автоматически — вручную ничего читать и писать
не нужно:

| Агент | Фаза | Что делает |
|---|---|---|
| `vault-domain-architect` | 1.2 | Проектирует карту доменов по всему vault за один вызов: собирает словари заметок, определяет границы, раскладывает файлы по темам |
| `vault-domain-analyzer` | 2 | Уходит в каждый домен параллельно, заполняет поля заметок и строит темы с оценкой проработки |

Первый агент — единственный, кто решает границы доменов. Он может создать
домен, объединить два, разделить один или переименовать. Второй границы не
меняет: если изнутри домена видно, что он собран неверно, он сигналит через
поле `boundary_flags`, и сигнал доходит до вас.

## Просмотр результата

Запустите дашборд:

```bash
start-dashboard.bat
```

Скрипт поднимет локальный HTTP-сервер на порту 8787 и откроет
`dashboard.html` в браузере — там доступна фасетная навигация по доменам,
типам контента и learning paths.

## Структура `taxonomy.json`

```jsonc
{
  "metadata": {
    "total_files": 54,          // файлов в доменах
    "all_files_count": 75,      // все .md в vault, включая отсеянный шум
    "projects_count": 13,
    "unclassified_count": 4,
    "total_domains": 9
  },
  "domains": [ /* домены: файлы, темы, learning_paths, recommended_topics */ ],
  "global_facets": { /* значения фасетов: типы, парадигмы, технологии */ },
  "statistics": { /* total_files (только домены), projects_count, распределения */ },
  "projects": {
    "count": 13,                // файлов, не число проектов
    "items": [{ "name": "Проект", "why": "почему это проект", "files": ["путь.md"] }]
  },
  "unclassified": {
    "count": 4,
    "items": [{ "path": "путь.md", "reason": "почему не легла", "suggestion": "что завести" }]
  },
  "filtered_out": { "count": 4, "files": [{ "path": "...", "reason": "empty_content" }] }
}
```

Арифметика, которую проверяет `synthesize_taxonomy.py`:

```
total_files + projects.count + unclassified.count + filtered_out.count == all_files_count
```

Вторая проверка, `files_exist`, сверяет каждый учтённый путь с vault: счёт
может сойтись, а путь быть переписан агентом с опечаткой. В полном прогоне это
`FAIL` (в `--merge` - `WARN`, потому что удалённые файлы остаются в
таксономии законно).

Проверить готовый файл, ничего не пересобирая:

```bash
python .claude/skills/semantic-taxonomy/scripts/synthesize_taxonomy.py --verify
```

Код возврата 1, если какая-либо проверка дала `FAIL`. Старые `taxonomy.json`
без новых секций проверку покрытия пропускают (`SKIP`), а не падают.

## Структура репозитория

```
obdidian_vault_performance/
├── CLAUDE.md              ← правила репо и навигация для Claude Code
├── CHANGELOG.md           ← история изменений
├── dashboard.html          ← веб-дашборд для просмотра taxonomy.json
├── start-dashboard.bat     ← запуск локального сервера + открытие дашборда
├── requirements.txt        ← python-зависимости
├── .env / .env.example     ← VAULT_PATH и другие переменные окружения
├── demo/                   ← демо-дашборд с фейковыми данными (GitHub Pages)
└── .claude/
    ├── agents/                   ← vault-domain-architect, vault-domain-analyzer, vault-relevance-finder, vault-topic-reassessor
    ├── skills/
    │   ├── semantic-taxonomy/    ← SKILL.md, scripts/ (пайплайн таксономии), references/
    │   └── analyze-vault-domain/ ← references/ (схема и примеры анализа домена)
    ├── plans/                    ← технические планы (PLAN.md и датированные файлы)
    ├── retrospectives/           ← рефлексия по сессиям
    └── temp_files/               ← временные файлы анализа (чистятся scripts/cleanup.py)
```

Пайплайн Фазы 1:

```
collect_vault_structure.py --scan   [Python]  список заметок, отсев мусора
        ↓
vault-domain-architect × 1         [Agent]   карта доменов + раскладка файлов
        ↓
collect_vault_structure.py --collect [Python]  структура + обновление кеша
```

## Важно

- `.env` содержит путь к вашему личному vault — не публикуйте его.
- `taxonomy.json` может содержать выдержки из содержимого ваших заметок —
  учитывайте это перед тем, как делиться файлом.
- Повторный запуск анализа в режиме Incremental не отслеживает удалённые,
  переименованные или перемещённые файлы — для полной синхронизации
  используйте режим Full.
- Если кажется, что фильтр отсеял что-то ценное, проверьте секцию
  `filtered_out` в `taxonomy.json` — там список исключённых файлов с причиной.
- Если кажется, что какие-то заметки выпали из анализа, проверьте секции
  `projects` и `unclassified` — там всё, чему архитектор не назначил домен.
  Дашборд показывает их отдельными блоками и подсвечивает в шапке любое
  расхождение по числу файлов.
